# 卡片链接阅读（qq-card-reader）

让机器人真正看懂 QQ 里的**卡片消息**——就是聊天记录里只剩一个 `[卡片消息]` 的那种。

## 它是干什么的

群里常见这种消息，正文里**只有一个占位符，没有任何网址**：

> 群友：[卡片消息]

这是 QQ 的小程序分享 / 公众号文章 / 音乐、视频、新闻卡片。机器人原本只看到 `[卡片消息]` 四个字，
卡片里写了什么、指向哪，它一概不知道 —— 只能猜或者装没看见（猜是最糟的：一本正经说错内容）。

装了这个技能之后发生了什么：

1. 机器人手里多了一个工具 `qq-card-reader__read_card`；
2. 遇到卡片时它可以调这个工具，传那条消息的 `#id`（例如 `-1743558115`）；
   别人**引用/回复**的卡片也行（正文显示 `[引用 …：[json]]`）：传那条回复消息的 `#id`，
   工具会顺着 `reply` 段去找被引用的那张卡片；
3. 工具**按消息 id 去协议端把卡片的原始数据取回来**（关键一步，见下），
   从卡片 JSON 里取出可访问的网址 → 跟随短链跳转 → 抓回网页 → 提取标题/摘要/正文；
4. 抓通之后把解析出来的真实地址**写回存档**，下次再问同一张卡片不用重新解析；
5. 抓不到就返回**明确结论**，并叮嘱模型照实说读不到、**绝不编内容**。

## 为什么必须按 messageId 去协议端取（这是整个技能的核心）

核心代码在收消息时就把卡片压成了占位符：

- `src/onebot.js` 的 `segmentsToText` 把 `json` 段渲染成 `[卡片消息]`；
- `extractMediaFromSegments` 只挑 image / video / face，**json 段一个字段都不留**。

也就是说 **URL 在入库那一刻就没了**，存档里永远只有那四个字 —— 光看存档，谁来都读不出来。

但协议端（SnowLuma / NapCat，OneBot v11 的 `get_msg`）**按 message_id 仍然能把原始消息段取回来**：
里面就是当初那个 `json` 段，`card` 字段里写着完整卡片 JSON，含 `meta.detail_1.qqdocurl` 之类的跳转地址。
所以这条链路是：

```
messageId → get_msg → 原始 json 段 → 卡片 JSON → 内容 URL → 抓网页 → 标题/摘要/正文
```

**这是"正文只有 [卡片消息]"唯一的出路。**

选 URL 时的讲究（一张卡片里通常有 3~5 个网址，挑错不如不挑）：

- 内容键优先：`qqdocurl` / `jumpUrl` / `targetUrl` / `url` …；
- 图标、封面、缩略图键（`icon` / `preview` / `cover` …）一律排最后，不会拿它当正文；
- 去掉 `_wv` / `from` 这类 WebView 专用参数（带着它常被要求"请用手机打开"）；
- 卡片里**只有**图标/封面（纯小程序卡片）→ 判定「没有可访问的网页地址」，
  照实说"这卡片我点不开"，而不是硬编内容。

## B 站视频卡片（v1.2.0）

B 站视频卡片走一条专用分支，比通用网页抓取多拿四类信息：

1. 直链（`bilibili.com/video/BV…` / `av…`）**先查公开接口**，一次拿到标题、简介、UP 主、
   播放量/点赞/投币/收藏/转发、时长、分 P 列表和封面；
2. `b23.tv` 短链先跟随跳转，落地页是 B 站视频时再补一次接口（失败就只用网页正文）；
3. 封面下载后作为 `image_url` 直接交给模型——**前提是模型能看图**。设置里关掉“附带 B 站视频封面”、
   或模型显式传 `cover:false` 时只回文字；视觉不可用时会自动降级，不会把纯文字模型喂到 400；
   **只有 B 站视频卡片会附封面**：公众号、新闻等普通网页卡片即使页面有 `og:image`，也只回文字，不下载、不塞图；
4. 接口被风控（`-412`）或改版时，**静默退回原来的 HTML 抓取**，标题/简介照常读；
   直链接口失败后不会原地重试，只有 `b23.tv` 短链落地到视频时才补取一次。

边界要记住：**封面只是视频的一张截图/海报，不是视频内容**。这里不下载视频、不抽帧，
所以不要对群友说“我看过这个视频”。

**封面只看主模型能力**：如果主模型被判定不能看图，即使设置里另配了“图片专用模型”，
本版也不会附带封面（核心的 `visionEnabled` 只看主模型，本单不改 `src/`）。

成本：文字元数据通常几百 token；封面一张大约 300–1,600 token（取决于压缩尺寸和视觉模型）。
更大的开销来自“整轮请求切到图片专用模型”——**前提是设置里配了「图片专用模型」**；
如果主模型是便宜的文字模型、视觉模型贵 3–5 倍，这一轮的总成本大约是无封面时的 1.3–2.5 倍。
只想知道标题/UP 主时，让模型传 `cover:false` 即可；普通网页卡片不会触发这笔开销。

## 为什么是「技能」而不是「插件」

按项目规范：**规则能写死 → 插件（`plugins/`）；要理解人话 → 技能（`skills/`）**。

这张卡片值不值得读（有人在问我吗？跟话题有关吗？）、读到了怎么接话，都要模型判断，
没有能写死的规则 → 注册工具进模型的 function 列表 → 落在 `skills/`（LLM 型）。

## 装了什么 / 放哪了

```
resources/app/skills/qq-card-reader/
  skill.json    清单（id、显示名、工具声明、设置项）
  index.js      实现（卡片解析 + 安全抓取 + 正文提取 + 工具注册）
  README.md     本文件
```

热重载开着，文件落盘就自动生效，不需要重启。

## 在「技能」页会看到什么

- 名字：**卡片链接阅读**（id `qq-card-reader`，v1.2.0，分类 knowledge）
- 状态：已启用 / 已加载 / 可用
- 工具：读取卡片消息（`qq-card-reader__read_card`）
- 设置项：

| 设置 | 默认 | 说明 |
|---|---|---|
| 启用卡片链接阅读 | 开 | 总开关。关掉后模型手里没这个工具，遇到卡片又回到"看不见"的状态 |
| 自动注入用法说明 | 开 | 每轮往提示词里放一小段用法。关掉省 token，但机器人更容易想不起来用 |
| 正文最多给模型多少字 | 6000 | 抓回来的正文截断长度（800~20000） |
| 附带 B 站视频封面 | 开 | 只对 B 站视频卡片生效，普通网页卡片不附封面；模型不能看图时自动跳过，只回文字 |
| 抓取超时（毫秒） | 15000 | 3000~60000。**整次读取的总预算**（含逐个尝试候选链接），不是每个链接各等一次 |
| 自定义 User-Agent | 空 | 留空时对公众号/短视频分享页自动用手机微信 UA |
| 不抓这些域名 | 空 | 逗号分隔。默认另外还跳过网盘类（pan.baidu.com / pan.quark.cn 等） |

## 抓取这块踩过的坑（都修好了，记下来免得再犯）

1. **不能优先用核心的 `src/safe-fetch.js`**。它用 `node:http` 裸请求，**不自动解压 gzip**，
   而一大片站点（B站、b23.tv…）默认回 gzip —— 压缩字节被它按 UTF-8 "解码"成一堆 U+FFFD，
   正文和标题全毁。表现极具迷惑性：HTTP 200、有四五万字节"内容"，就是提不出标题。
   它还只读 **50000 字符**，公众号那种 3 MB 的图文页会被截掉大半。
   所以抓取改成**内置防护优先**（走 Node 全局 fetch，自动解压 gzip/deflate/br，
   还能按 charset 正确解 GBK，并且认设置里的超时与 UA），核心 safeFetch 只作为兜底。
2. **JS 渲染页没有静态正文**。B站移动端、知乎这类页面正文全靠 JS，
   静态 HTML 抓出来 0 字。现在会在正文明显为空时，从 SSR 数据块
   （`__INITIAL_STATE__` / `__NEXT_DATA__` / `__NUXT__`）里捞简介 —— 实测能把
   视频的真实简介文字捞出来。
3. **分享页的 description 是拼接垃圾**：`简介：<标签残渣>；已有355名玩家推荐…；更多实用攻略…`。
   现在会解码两遍实体、切掉被截断在标签中间的尾巴、剔掉站点推广段，挑信息量最大的那一段。
4. **超时曾经是"每跳"而不是"整次"**：重定向最多 6 跳、候选链接最多 5 个，最坏能等 90 秒以上。
   现在设置里的超时是整次读取的总预算，候选链接、重定向、核心兜底共用同一份时间。

## 安全说明

这条链路是"群友发什么卡片就去抓什么"，所以防护是完整的：

- 只 http/https；禁止 URL 内嵌凭据；裸 IP、`file://` 一律拒绝；
- 域名先做 DNS 全量解析，**任一解析结果落在内网/环回/链路本地/CGNAT 就拒绝**；
- 每跳校验出的公网 IP 会**全部钉给连接层**（undici Agent 自定义 lookup），域名不会在校验后被二次解析，防 DNS rebinding；首个地址不可达时可在其余已校验地址间回退；
- 手动逐跳跟随重定向（最多 5 跳），**每一跳都重新校验** —— 防"公网 302 到内网"；
- 响应体限量读取（6 MB 上限），超量即断开；
- 写进存档的只有地址本身，不落任何抓回来的正文。

## 已知边界（照实说，不硬编）

- **纯小程序卡片**：卡片 JSON 里确实只有标题/图标/小程序入口，没有可访问网址 → 读不到，
  会明确告诉模型"这张卡片里没有可访问的网页地址"。
- **链接过期**：卡片里的分享地址带 rkey，是**限时**的，发出来太久会 403/404 →
  会提示请群友重发。协议端也会清理老消息，这一步会返回"取回原始消息失败"。
  写回存档的是**这次实际抓通的地址**：B 站这类落地页通常长期可用，公众号链接仍可能带 rkey，几小时后照样过期。
- **要登录的页面**：抓取不带任何 cookie/登录态（百度贴吧这类会直接给"百度安全验证"页）→ 读不到。
- **视频画面**：能拿到标题、简介、UP 主、播放量、时长和**封面图**，但拿不到视频本身；
  封面只是一张截图，不代表完整内容。不下载视频、不抽帧。
- **封面只在主模型能看图时附带**：主模型被判定不能看图时，即使另配了“图片专用模型”也不会带封面；
  普通网页卡片一律不附封面。
- 核心兜底（undici 软加载失败时）仍只取 DNS 的第一个地址，没有多地址回退；正常路径已钉全部已校验地址。

## 自测

`index.js` 的纯函数都是导出的，回归测试固化在 `test/qq-card-reader-test.mjs`（`npm run test:card`，25 项，全部离线；所有请求都由假 fetch 驱动）。
另做过一轮一次性自测，覆盖：

- 卡片 JSON → URL：标准卡片、**双层转义**、`\u0026`、XML 卡片、内容键优先、不拿图标/封面、
  `_wv` 参数剥离、纯小程序卡片判定；
- messageId → get_msg：正常卡片、无 URL 卡片、非卡片消息、`get_msg` 报错、没有协议端连接；
- 端到端（正文只有 `[卡片消息]`）：能读到内容、写回存档、无 URL 时照实说打不开、
  403 时说链接过期、取不到消息时说清卡在哪一步、只给 url 时不碰协议端；
- 抓取安全：内网/环回/私有段/`file://`/带凭据 URL 全拒、重定向逐跳校验、
  重定向到内网被拦、重定向次数上限；
- 正文提取：脚本样式剥离、`js_content` 容器优先、实体解码、截断、
  `cleanDescription`、SSR 数据块兜底、括号配平、静态正文不被覆盖。

**并用真实的协议端 + 真实群里的卡片消息跑过全链路**：5 条真实卡片全部解析出
`b23.tv` 地址并成功抓到对应的 B站视频页（标题/简介/正文齐全）。

## 排障

- **技能页显示"加载失败"**：把页面那句原因原样发出来。最常见是 `skill.json` 少逗号，
  或 `index.js` 语法错误 —— 两者都会让整条技能不可用。
- **显示已启用但机器人还是当没看见卡片**：先确认「自动注入用法说明」是开的；
  直接在群里 @ 它问"这张卡片里写了啥"，通常就调工具了。
- **总是"取回原始消息失败"**：那条消息在协议端已经被清理了 ——
  这种情况只能让群友重发，或者把卡片里的网址单独贴出来。
- **总是"没有可访问的网页地址"**：那是真的纯小程序卡片，属于已知边界。
